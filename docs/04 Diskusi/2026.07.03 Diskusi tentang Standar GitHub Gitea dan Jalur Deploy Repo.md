## Pemicu

Diskusi ini lahir setelah repo lokal berhasil:

- diinisialisasi sebagai repository Git
- dihubungkan ke dua remote aktif
- dipush ke GitHub
- dipush ke Gitea setelah jalur autentikasi dipindahkan dari HTTP ke SSH

Temuan operasional tersebut cukup penting untuk dijadikan bahan diskusi formal karena menyentuh:

- source of truth operasional repository
- urutan publish harian
- standar autentikasi remote
- kemungkinan jalur deploy aktif di masa berikutnya

### Kondisi repo yang terverifikasi

- branch aktif saat audit adalah `main`
- remote aktif saat audit terdiri dari:
  - `origin` yang mengarah ke GitHub melalui HTTPS
  - `gitea` yang mengarah ke Gitea melalui SSH
- push ke GitHub sempat ditolak karena remote sudah memiliki initial commit bawaan
- push ke Gitea sempat gagal saat remote masih memakai HTTP karena autentikasi tidak tersedia
- setelah remote Gitea memakai SSH dan key lokal tervalidasi, push ke Gitea berhasil
- pada saat audit, branch `main` lokal, GitHub, dan Gitea sudah berada pada commit yang sama

### Temuan dari dokumen aktif yang beririsan

- `docs/README.md` sudah menetapkan urutan publish wajib `commit -> push -> deploy`
- `docs/README.md` belum menetapkan apakah deploy aktif nanti berasal dari GitHub, Gitea, atau keduanya
- `docs/01 Profil Sistem/PROJECT_STATUS.md` masih menandai area deploy dan keputusan domain sebagai `rencana`
- `docs/04 Diskusi/README.md` mewajibkan topik seperti ini tetap hidup sebagai diskusi dulu sebelum melahirkan keputusan atau referensi teknis
- `AGENTS.md` sudah melarang lompatan lifecycle, tetapi belum memuat aturan khusus dual-remote

### Gap atau konflik yang terdeteksi

- dual-remote sudah berjalan secara faktual, tetapi belum memiliki keputusan normatif aktif
- jalur deploy aktif belum diputuskan, padahal urutan publish sudah mengasumsikan deploy sebagai tahap resmi
- nama remote lokal sudah konsisten untuk sesi ini, tetapi belum ada standar apakah penamaan itu wajib dipertahankan
- belum ada aturan tertulis apakah setiap commit yang siap rilis wajib selalu dipush ke GitHub dan Gitea secara identik
- belum ada referensi teknis resmi untuk setup SSH, verifikasi remote, atau checklist push

## Opsi yang Dipertimbangkan

- **Opsi A: GitHub sebagai mirror, Gitea sebagai jalur deploy aktif**
  - Kelebihan:
    - selaras dengan pola yang terbukti berhasil di repo pembanding
    - memisahkan fungsi kolaborasi umum dan fungsi operasional deploy
    - cocok dengan fakta bahwa autentikasi Gitea saat ini sudah sehat melalui SSH
  - Kekurangan:
    - membutuhkan disiplin sinkronisasi dua remote
    - perlu keputusan tegas agar GitHub tidak diam-diam dipakai sebagai jalur deploy lain

- **Opsi B: GitHub dan Gitea hanya sebagai mirror setara, deploy ditentukan nanti**
  - Kelebihan:
    - paling ringan untuk fase bootstrap
    - tidak memaksa keputusan deploy sebelum infrastruktur siap
  - Kekurangan:
    - menyisakan ambiguitas operasional
    - berisiko membuat agent atau developer berbeda tafsir saat publish

- **Opsi C: Satu remote operasional utama, remote lain opsional**
  - Kelebihan:
    - lebih sederhana secara operasional
    - meminimalkan risiko divergensi commit antaremote
  - Kekurangan:
    - bertentangan dengan kondisi aktual yang sudah memakai dua remote
    - mengurangi manfaat redundancy dan mirror

## Poin Diskusi

### 1. Apakah dual-remote sudah layak dianggap standar repo

Secara fakta operasional, repo ini sudah berhasil hidup di dua remote dan keduanya sudah sinkron pada branch `main`. Itu berarti pembahasan bukan lagi soal kemungkinan teknis, tetapi soal apakah perilaku ini ingin dikunci sebagai standar resmi.

Jika iya, keputusan final nanti perlu menegaskan:

- dua remote mana yang wajib dipertahankan
- apakah semua commit siap rilis wajib hadir di keduanya
- apakah sinkronisasi identik adalah syarat sebelum pekerjaan dianggap selesai

### 2. Peran GitHub vs Gitea masih perlu dipisahkan secara normatif

Saat ini GitHub terbukti menjadi remote yang lebih mudah diakses untuk kolaborasi umum, sedangkan Gitea terbukti memerlukan jalur SSH yang lebih spesifik. Ini memberi sinyal alami bahwa dua remote tersebut mungkin memang punya fungsi berbeda.

Namun perbedaan fungsi itu belum sah sebagai norma sampai ditetapkan. Tanpa keputusan, ada beberapa risiko:

- seseorang bisa menganggap GitHub adalah jalur deploy
- seseorang bisa menganggap push ke salah satu remote saja sudah cukup
- workflow CI/CD di masa depan bisa lahir di tempat yang salah

### 3. Standar autentikasi Gitea sudah punya fakta kuat

Audit sesi ini menunjukkan pola berikut:

- HTTP tanpa kredensial gagal untuk push ke Gitea
- SSH berhasil
- key lokal yang aktif sudah diterima server Gitea

Karena itu, jika topik ini difinalkan nanti, referensi teknis sangat mungkin perlu mencatat bahwa jalur operasional Gitea untuk repo ini memakai SSH, bukan HTTP anonim.

### 4. Jalur deploy aktif belum boleh diasumsikan

Walau pola repo pembanding cenderung memakai Gitea sebagai jalur deploy aktif, repo `kctrimatra` belum memiliki:

- workflow deploy
- secret CI/CD
- branch deploy formal selain `main`
- prosedur smoke test pascadeploy

Jadi untuk kondisi saat ini, diskusi tidak boleh langsung menulis seolah deploy aktif dari Gitea sudah final. Yang sudah boleh dicatat hanya:

- dual-remote nyata sudah ada
- publish ke dua remote sudah berhasil
- keputusan tentang jalur deploy aktif masih menunggu penetapan

### 5. Penamaan remote lokal perlu dipertimbangkan

Saat audit, nama remote yang dipakai adalah:

- `origin` untuk GitHub
- `gitea` untuk Gitea

Ini cukup jelas, tetapi ada opsi lain yang umum dipakai di repo lain, misalnya menjadikan Gitea sebagai `origin` dan GitHub sebagai `github`. Jika repo ini ingin menjaga konsistensi lintas proyek, hal itu perlu diputuskan di level keputusan, bukan dibiarkan sebagai kebiasaan kebetulan.

### 6. Diskusi ini kemungkinan akan melahirkan dua dokumen berbeda

Jika difinalkan, hasil diskusi ini paling mungkin bercabang menjadi:

- satu keputusan normatif tentang standar remote Git dan sumber deploy aktif
- satu referensi teknis tentang setup remote, SSH, verifikasi koneksi, dan urutan push

Pemisahan itu penting agar:

- norma tidak bercampur dengan command teknis
- perubahan URL, key, atau langkah verifikasi tidak perlu selalu merevisi keputusan payung
