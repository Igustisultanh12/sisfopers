## Latar Belakang

Repo `kctrimatra` membutuhkan fondasi dokumentasi yang kuat sejak masih berada pada tahap bootstrap. Struktur lifecycle dokumen dan guardrail dasar sudah hidup di beberapa README dan `AGENTS.md`, tetapi belum memiliki satu keputusan payung yang memegang norma formal aktif.

Keputusan ini lahir untuk:

- membakukan identitas dokumen aktif
- menegaskan rumah dokumen dan otoritasnya
- menetapkan batas aksi agent saat topik masih berada pada level diskusi
- mengunci prinsip workplan, QA, dan referensi teknis
- mencegah drift instruksi antar dokumen aktif sejak awal pertumbuhan repo

## Scope

### Termasuk

- identitas dokumen formal aktif

- rumah `10 Referensi Internal`

## Keputusan

1. Dokumen formal aktif wajib memakai identitas stabil yang mengikuti keluarga dokumennya, bukan status sementara.
2. Format identitas aktif yang dipakai:
   - keputusan: `YYYY.Kep.XXX`
   - rencana kerja: `YYYY.MM.DD Rencana Kerja tentang Judul Dokumen.md`
   - diskusi: `YYYY.MM.DD Diskusi tentang Judul Dokumen.md`
   - referensi teknis: `YYYY.11.XXX`
3. Aturan perubahan identitas keputusan ini berlaku mulai sejak keputusan ini ditetapkan dan tidak berlaku surut terhadap dokumen keputusan lama yang belum disentuh.
4. Dokumen keputusan lama dengan identitas `YYYY.02.XXX` tetap sah sepanjang belum direvisi setelah keputusan ini berlaku.
5. Jika dokumen keputusan lama direvisi setelah keputusan ini berlaku, identitas file dan metadata dokumen tersebut wajib dinormalisasi ke format `YYYY.Kep.XXX`.
6. Prefix status tidak dipakai pada dokumen aktif. Prefix status hanya sah di `docs/00 Arsip/`.
7. Status arsip yang sah adalah:
   - `[DICABUT]`
   - `[SELESAI]`
   - `[DITETAPKAN]`
   - `[HISTORIS]`
8. Semua dokumen formal aktif wajib memakai metadata formal umum yang seragam.
9. `02 Keputusan` memegang source of truth normatif aktif.
10. `03 Rencana Kerja` memegang pelaksanaan turunan keputusan.
11. `04 Diskusi` memegang pembahasan sebelum finalisasi.
12. `11 Referensi Teknis` memegang panduan teknis, checklist, template implementatif, blueprint, SOP, atau dokumen operasional turunan yang menjabarkan keputusan aktif, tetapi tidak memiliki otoritas pencabutan normatif.
13. `10 Referensi Internal` memegang artefak sumber internal yang perlu dipertahankan di repo karena tidak bisa diserap memadai ke keputusan, diskusi, atau workplan.
14. Rumah `10 Referensi Internal` minimal dibagi ke taxonomy:
   - `Undang-Undang`
   - `Peraturan`
   - `Peraturan Menteri`
   - `Keputusan Menteri`
   - `Edaran`
   - `Lainnya`
15. Referensi hukum atau artefak sumber yang dipertahankan wajib tersimpan di repo dan tidak boleh bergantung hanya pada file eksternal.
16. `Surat Keputusan` yang menjadi dasar pembentukan atau perubahan entitas domain aktif diperlakukan sebagai artefak sumber sah dan hidup di rumpun `Keputusan Menteri`.
17. Untuk `Surat Keputusan` massal, struktur minimum artefak yang dianggap cukup adalah satu artefak sumber, satu ringkasan, dan satu indeks nama.
18. Satu artefak sumber boleh direuse lintas proses domain selama konteks penggunaannya sah menurut keputusan domain masing-masing.
19. Keputusan hanya boleh dicabut oleh keputusan.
20. Dokumen profil sistem di `01 Profil Sistem` adalah referensi aktif yang menggambarkan kondisi repo, baseline, atau asumsi teknis, tetapi tidak menyalip keputusan sebagai norma aktif.
21. Agent wajib memilih urutan kerja dokumen paling hemat jejak: `revisi -> rename -> arsip -> file baru`.
22. `Hapus lalu buat ulang` tidak sah sebagai pendekatan default bila `revisi` atau `rename` masih cukup.
23. Perubahan mikro wajib memakai delta edit minimum yang memadai.
24. Selama topik masih berada pada level diskusi dan belum final secara lifecycle, agent dilarang melahirkan keputusan, rencana kerja, referensi teknis, manual, referensi operasional, spesifikasi, blueprint, SOP, atau template implementasi baru di rumah aktif lain.
25. Jika user meminta dokumen turunan saat topik masih diskusi, kebutuhan itu wajib ditahan dan dicatat di dokumen diskusi aktif sampai keputusan final lahir atau user memberi override lifecycle yang eksplisit.
26. Jika user masih bekerja pada level diskusi, itu tidak otomatis memberi izin untuk menyentuh keputusan aktif, workplan aktif, changelog, atau file runtime lain di luar yang benar-benar diperlukan oleh scope diskusi.
27. Jika ada konflik antara keputusan aktif dan pedoman turunan, keputusan aktif menang. Drift tersebut wajib dicatat dan diselaraskan.
28. Workplan aktif wajib merujuk minimal satu keputusan aktif, memakai schema operasional yang eksplisit, dan tidak boleh menafsir ulang keputusan.
29. Validasi workplan wajib berbasis teks normatif final yang benar-benar tertulis pada keputusan, README, dan instruksi agent aktif. Validasi berbasis niat atau kesan arah dokumen tidak sah.
30. Workplan tidak boleh diarsipkan otomatis hanya karena implementasi tampak selesai. Sebelum penutupan normatif, wajib ada QA user atau keputusan eksplisit user untuk `skip QA`, dan kondisi itu harus dicatat jujur.
31. Jika sinkronisasi pascakeputusan hanya ringan dan terbatas, ia boleh langsung dikerjakan.
32. Jika sinkronisasi pascakeputusan banyak, kompleks, menyentuh banyak clause lintas dokumen, atau butuh verifikasi bertahap, wajib lahir workplan formal di `03 Rencana Kerja/`.
33. Dokumen teknis operasional seperti setup remote, SSH, verifikasi push, checklist teknis, atau panduan langkah kerja hidup sebagai referensi teknis turunan, kecuali di kemudian hari lahir keputusan normatif baru yang membutuhkannya.
34. Setiap field waktu berlabel `WIB` wajib memakai waktu eksekusi aktual `UTC+07:00`.

## Aturan Detail

### A. Aturan Penamaan

- nama file aktif memakai identitas formal dan judul yang stabil
- kata sambung atau preposisi seperti `tentang`, `dan`, `di`, `ke`, `dari`, `untuk`, dan `yang` tetap huruf kecil pada judul dokumen
- nama file boleh memakai spasi biasa
- slug judul tidak boleh mengandung kata status seperti `final`, `revisi`, `fix`, atau `baru`
- keputusan aktif wajib memakai identitas formal `YYYY.Kep.XXX` pada metadata dan nama file sejak keputusan ini ditetapkan
- untuk rencana kerja dan diskusi, field `Identitas dokumen` wajib mengikuti nama file aktif tanpa ekstensi
- judul setelah kata `tentang` harus spesifik dan stabil

### B. Metadata Formal Umum

Blok metadata formal umum yang dibakukan:

```md
Status: Berlaku
Tanggal penetapan: DD Bulan YYYY
Identitas dokumen: YYYY.AA.XXX
Jenis dokumen: Keputusan
Domain: kctrimatra
Topik: ...
Keputusan induk: -
Turunan dari: -
Mengubah: -
Mencabut: -
Digantikan oleh: -
```

### C. Aturan Transisi dan Arsip

- dokumen aktif yang final tidak berubah rumah lifecycle tanpa jejak arsip yang jujur
- lebur dokumen hanya sah bila dokumen sumber dipindahkan ke arsip dengan status yang sesuai, alasan yang jujur, timestamp `WIB`, dan rujukan ke penerus
- field `Dicabut oleh` pada arsip keputusan wajib menunjuk keputusan yang mencabut
- `Dokumen referensi teknis terkait` hanya dipakai untuk menandai rumah substansi implementatif turunan, bukan sebagai pencabut keputusan
- format keputusan `YYYY.Kep.XXX` berlaku mulai sejak keputusan ini ditetapkan dan tidak berlaku surut
- keputusan lama `YYYY.02.XXX` tetap sah sepanjang belum direvisi setelah keputusan ini berlaku
- saat keputusan lama direvisi setelah keputusan ini berlaku, identitas file dan metadata dokumen itu wajib dinormalisasi ke `YYYY.Kep.XXX`

### D. Aturan Workplan

- schema workplan formal aktif wajib eksplisit dan dapat diaudit
- heading minimum workplan aktif mengikuti pedoman `03 Rencana Kerja`
- jika QA user belum terjadi, workplan boleh tetap aktif walau implementasi substantif sudah selesai
- jika user memerintahkan `skip QA`, kondisi tersebut wajib dicatat jujur
